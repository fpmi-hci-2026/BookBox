# Лабораторная работа №4

## Стили интеграции программных систем и проектирование API

**Проект:** BookBox — онлайн-магазин книг.

**Группа:** 11.

**Состояние отчёта:** 25 ноября 2026 года; задания 1–4 выполнены, API спроектирован и проверен на Mock-сервере.

## Цель работы

Цель лабораторной работы — спроектировать и задокументировать API BookBox: уточнить модель требований и данных, определить маршруты и конечные точки, описать контракт в OpenAPI и проверить его с помощью Mock-сервера.

Входными данными служат требования, пользовательские истории, варианты использования и модели процессов из [ЛР3](lab3.md). Подробные материалы текущего этапа собраны в [каталоге ЛР4](lab4/README.md). В условии лабораторной (`task.md`) предусмотрены четыре задания; они выполнены в полном объёме.

## 1. Модель требований и реестр вариантов использования

Для определения объёма API использованы роли и сценарии BookBox из ЛР3. Модель связывает действующих лиц, пользовательские истории и варианты использования, а затем сопоставляет их с требованиями к API. Для проверки полноты операций учтена [CRUD-модель управления каталогом интернет-магазина GetAnalyst](https://getanalyst.ru/database/CRUD-2).

В модель включены роли гостя, покупателя, администратора, аналитика и платёжного провайдера. Истории US-01–US-10 взяты из ЛР3. Добавлены US-11–US-14 для регистрации и входа, управления корзиной и избранным, отзывов, истории заказов и уведомлений.

Составлен реестр из 12 требований API и 14 вариантов использования. Он охватывает каталог и поиск, аккаунты, корзину, избранное, заказ и оплату, предзаказ, уведомления, отзывы, административные действия и аналитику. Отдельно зафиксированы правила доступа: покупатель видит только собственные данные, административные действия требуют соответствующей роли, а повторные команды оплаты и передачи заказа должны обрабатываться безопасно.

Результат: [модель требований и реестр Use Case](lab4/requirements.md).

## 2. Логическая и физическая модели базы данных

Логическая модель уточняет предметную модель ЛР3 для выбранных API-сценариев. В неё входят 18 сущностей, включая аккаунты и роли, каталог книг и справочников, корзину и избранное, заказы и позиции заказа, попытки оплаты, предзаказы, отзывы и уведомления.

Для физической схемы выбрана PostgreSQL 13+ как предварительное проектное решение. В модели заданы первичные и внешние ключи, уникальность email и связей, ограничения количества и денежных значений, статусы заказов, платежей и отзывов, а также индексы для чтения заказов, отзывов и уведомлений. Позиция заказа хранит цену на момент покупки; попытки оплаты имеют ключ идемпотентности.

Подготовлены [логическая модель](lab4/logical-model.md), [физическая ER-модель](lab4/physical-model.md), её [исходник PlantUML](lab4/physical-model.puml) и [SQL-схема PostgreSQL](lab4/schema.sql). SQL-файл описывает создание структуры пустой базы данных и не требует наличия приложения. В рамках текущего этапа PostgreSQL не разворачивался, а SQL не выполнялся.

Выбор PostgreSQL нужно подтвердить при интеграции с BookBox-Server. Репозиторий сервера пока содержит только README, поэтому совместимость схемы с ORM и кодом backend ещё не проверена.

## 3. Маршруты и спецификация API

Маршруты спроектированы как ресурсные и покрывают все 14 вариантов использования. Базовый URL — `https://api.bookbox.example/v1`; данные передаются в JSON, ошибки — в `application/problem+json` по RFC 7807.

| Область | Маршруты | Доступ |
|---|---|---|
| Каталог | `/books`, `/books/{bookId}`, `/genres`, `/publishers` | публично |
| Аккаунт | `/auth/register`, `/auth/login`, `/me` | публично / Bearer JWT |
| Корзина и избранное | `/me/cart`, `/me/cart/items/{bookId}`, `/me/favorites`, `/me/favorites/{bookId}` | Bearer, роль `buyer` |
| Заказы | `/me/orders`, `/me/orders/{orderId}`, `/me/orders/{orderId}/payment-attempts` | Bearer, роль `buyer` |
| Платёжный провайдер | `/payments/{paymentAttemptId}/result` | подпись провайдера |
| Предзаказы и уведомления | `/me/preorders`, `/me/preorders/{preorderId}`, `/me/notifications`, `/me/notifications/{notificationId}` | Bearer, роль `buyer` |
| Отзывы | `/books/{bookId}/reviews`, `/admin/reviews`, `/admin/reviews/{reviewId}` | публично / `buyer` / `admin` |
| Администрирование | `/admin/books`, `/admin/books/{bookId}`, `/admin/orders/{orderId}/ship` | Bearer, роль `admin` |
| Аналитика | `/analytics/sales`, `/analytics/sales/export` | Bearer, роль `analyst` или `admin` |

Для каждого метода, меняющего состояние, определены тело запроса, схема и пример успешного ответа, коды `400`, `401`, `403`, `404`, `409`, `422`, `429` и `500`. Отдельно описаны идемпотентность оплаты через `Idempotency-Key` и безопасный повтор передачи заказа в доставку. Полная таблица «Use Case → HTTP-метод → маршрут», тела запросов и смысл статусов приведены в [реестре маршрутов](lab4/routes.md).

Машиночитаемый контракт — [OpenAPI 3.0.3](lab4/openapi.yaml); он содержит 34 операции, переиспользуемые схемы, примеры для POST/PUT/PATCH и единый формат ошибок. Для просмотра на GitHub Pages добавлена [страница Swagger UI](lab4/api.html).

## 4. Mock-сервер и проверка API

Для проверки контракта выбран **Prism 5.16.0** — локальный Mock-сервер, который читает OpenAPI-файл, отвечает примерами и валидирует запросы по схемам. Такой подход не требует внешней учётной записи, воспроизводим по команде и использует тот же контракт, который импортируется в SwaggerHub, Postman или Bruno.

Добавлены команды:

```bash
npm install
npm run mock:api   # Mock-сервер на http://127.0.0.1:4010
npm run test:api   # 43 проверки контракта
```

Проверены успешные и ошибочные сценарии поиска, регистрации и входа, корзины, создания заказа и нехватки остатка, оплаты и повторной оплаты, предзаказа, уведомлений, отзывов, запрета административного доступа, передачи заказа в доставку, аналитики и CSV-выгрузки. Все **43 из 43** проверок пройдены; протокол сохранён в [mock-test-results.json](lab4/mock-test-results.json).

Mock-сервер проверяет форму контракта, но не заменяет серверную бизнес-логику: реальные остатки, роли, владение заказом, подпись провайдера и идемпотентность должны проверяться интеграционными тестами BookBox-Server. Коды `401`, `403`, `404`, `409` в Mock-проверке выбираются заголовком `Prefer: code=...`, а `422` для неверной оценки отзыва получен настоящей валидацией схемы.

Подробные примеры запросов, порядок импорта в SwaggerHub/Bruno/Postman и ограничения описаны в [отчёте о Mock-проверке](lab4/mock-testing.md). Ссылки на документацию API: [Swagger UI](lab4/api.html) и [OpenAPI-файл](lab4/openapi.yaml).
