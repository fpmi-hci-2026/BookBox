## Задание 3 — маршруты и OpenAPI

1. Использовать требования API-FR-01–API-FR-12 и UC-01–UC-14 из `requirements.md`.
2. Согласовать с основным разработчиком ресурсные маршруты, методы, аутентификацию и формат ошибок; зафиксировать решения в OpenAPI 3.x.
3. Для каждого endpoint описать параметры, JSON-тело там, где оно требуется, схему успешного ответа, ошибки и статусы HTTP.
4. Добавить таблицу трассировки Use Case → HTTP-метод → маршрут.
5. Не вводить новые сущности, расходящиеся со схемой `schema.sql`, без согласования; если нужен API-ресурс для корзины, аккаунта или отзывов, он уже представлен в логической модели.
6. Результат: проверяемый файл спецификации и короткая документация по маршрутам в `docs/lab4/`.

### Предлагаемое разбиение ресурсов

`/books`, `/books/{bookId}`, `/auth/register`, `/auth/login`, `/me`, `/me/cart`, `/me/favorites`, `/me/orders`, `/orders/{orderId}`, `/orders/{orderId}/payment-attempts`, `/me/preorders`, `/me/notifications`, `/books/{bookId}/reviews`, `/admin/books`, `/admin/orders/{orderId}/ship`, `/admin/reviews/{reviewId}`, `/analytics/sales`.

Это исходный набор для проектирования, а не окончательно утверждённый контракт. Для действий, меняющих состояние, отдельно решить метод, повторяемость и проверку доступа.

## Задание 4 — Mock-сервер и проверка

1. Импортировать OpenAPI из задания 3 в выбранный сервис (SwaggerHub, Postman или Bruno).
2. Настроить Mock-сервер и заполнить примеры правдоподобными данными BookBox.
3. Прогнать хотя бы один успешный и один ошибочный сценарий для ключевых потоков: поиск, создание заказа/нехватка остатка, повтор оплаты, предзаказ, запрет административного доступа, аналитика.
4. Зафиксировать запросы, ответы, коды и ссылку на опубликованную документацию.
5. Результат добавить в `docs/lab4/` и обновить страницу API в локальной Wiki и GitHub Pages.

- Вторая часть не реализует сервер и не меняет Docker/CI — это следующие задания ЛР4.
